## 1. 무엇을 세는가 (스위치 0번 테이블)

접속 호스트마다 스위치 0번 테이블에 세는 규칙 7개를 둔다. 컨트롤러가 1초마다 읽어 `sdn:stats:flowcount`로 발행한다
(처음에는 2초였다. 탐지 시간을 줄이려고 1초로 바꿨다, §2.7. 포트 통계 · 서비스 상태는 그대로 2초).
패킷은 세기만 하고 1번(속도 제한) → 2번(전달 · 격리 · 우회) 테이블로 그대로 넘어간다. 그래서 격리 중에도 공격 패킷 수를 계속 셀 수 있다.

| 종류 | 일치 조건 | 쓰는 곳 |
|---|---|---|
| `syn` | in_port, TCP, SYN 있음 · ACK 없음 | SYN Flood (연결 요청만, 서버의 SYN-ACK 응답은 제외) |
| `fin` | in_port, TCP, FIN | SYN 짝 맞춤 |
| `rst` | in_port, TCP, RST | SYN 짝 맞춤 |
| `udp` | in_port, UDP | UDP Flood |
| `icmp` | in_port, ICMP | ICMP Flood |
| `rst_in` | 목적지 = 이 호스트, TCP, RST | 포트 스캔 (닫힌 TCP 포트의 거절) |
| `unreach_in` | 목적지 = 이 호스트, ICMP type 3 | 포트 스캔 (닫힌 UDP 포트의 도달 불가) |

파생 지표: `gap = syn − (fin + rst)` (짝이 안 맞는 연결 요청), `fail = rst_in + unreach_in` (받은 실패 응답).

스위치 카운터로 볼 수 없는 것은 세 곳에서 따로 받는다.

| 입력 | 어디서 | 채널 | 쓰는 곳 |
|---|---|---|---|
| `arp_fail` | 컨트롤러(Proxy ARP): 접속 호스트가 ARP로 물어본 **없는 내부 주소**의 누적 개수(서로 다른 주소) | `sdn:stats:flowcount`에 함께 | 내부 확산 |
| 서비스 상태 | 컨트롤러가 정상 사용자 자리(S1)에서 보호 서버로 0.2초마다 보내는 ICMP echo(가상 출발지 10.0.0.250)의 손실 · 왕복 시간, 2초마다 | `sdn:health:service` | 위험 단계의 서비스 악화 조건 |
| 서버 연결 | 서버 연결 수집기(`ss`)가 2초마다 센 접속 PC별 열린 HTTP 연결과 **느린 요청**(20초 넘게 요청이 안 끝나고 서버가 아직 응답을 안 보냄, 초당 500B 미만, Apache mod_reqtimeout과 같은 기준) | `sdn:stats:serverconn` | Slow HTTP |

## 2. 판단 기준

숫자는 Mininet 다이아몬드 토폴로지에서 실제 패킷으로 잰 값으로 정했다. 규칙은 하나다: **정상에서 잰 최댓값에 2배 여유.**

### 2.1 측정 방법

- 접속 호스트 2대(H_legit S1:1, H_attacker S1:2)가 [`traffic/normal_user.py`](../../traffic/normal_user.py)로 정상 사용자를 10분 흉내 낸다:
  ping(H_legit 0.05초 · H_attacker 1초 간격), 웹 요청(평균 1초), DNS 조회(평균 2초), 20MB 다운로드(약 60초마다),
  접속 몰림 2회(360초 · 480초, 30초씩), 닫힌 포트 실수(TCP 8080 · UDP 5353, 평균 45초마다).
- 이어서 H_attacker가 공격 9종을 하나씩 실행한다 (정상 트래픽은 계속 흐름, 공격 사이 30초 쉼).
- 값은 컨트롤러가 2초마다 발행한 세는 규칙 카운트(`sdn:stats:flowcount`)의 초당 변화량이다. 판단 프로그램이 보는 값과 같다.
- 실행: `sudo python3 -m harness.verification.criteria_measure --run --out <폴더> --normal-seconds 600 --surge-at 360,480`

### 2.2 정상 트래픽 평소값 (초당, 2초 보고 297회 × 2 호스트 — 2초 주기 때 측정)

| 지표 | 평균 (H_legit / H_attacker) | 표준편차 | 정상 최대 | 최소값 (최대 × 2, 10 단위 올림) |
|---|---|---|---|---|
| `syn` | 5.2 / 5.2 | 12.1 | 55 (접속 몰림) | **110** |
| `gap` = syn − (fin + rst) | 0.03 / 0.03 | 0.25 | 3.5 | **10** |
| `udp` | 0.48 / 0.49 | 0.45 / 0.51 | 2.5 | **10** |
| `icmp` | 17.9 / 0.98 | 0.36 / 0.10 | 18.5 | **40** |
| `fail` = rst_in + unreach_in | 0.03 / 0.02 | 0.11 | 1 (4초 창 2개, 5분 창 13개) | **10** |
| 포트 전체 수신 (참고) | 107 / 92 | — | 2,782 (다운로드 ACK) | — |

포트 · 지표별 평균과 표준편차는 [`model/criteria_baseline.json`](../../model/criteria_baseline.json)에 저장돼 있고, 추론 워커가 켜질 때 읽는다.
기준선 = max(평균 + 3 × 표준편차, 최소값). 기준선을 넘으면 주의(WATCH, 기록만).

### 2.3 숫자와 정한 방법

| 숫자 | 값 | 정한 방법 |
|---|---|---|
| 최소값 | 위 표 | 정상 최대 × 2, 10 단위로 올림 |
| N (UDP · ICMP Flood) | **10배** | 정상에서 최대가 평균의 약 5배(UDP 2.5 ÷ 0.49)까지 올라감 → 2배 여유 |
| 공격 최소 규모 | **초당 50개** (UDP · ICMP · SYN 차이) | 측정한 약한 공격(초당 100개)의 절반 → 약한 공격도 2배 여유로 잡힘. 평소가 0에 가까운 포트에서 10배가 너무 작은 수가 되는 것을 막음 |
| SYN Flood 누적 H | **100개** | 약한 공격(초당 100개)은 한 보고(2초) 안에 넘음. 정상 최대 차이 3.5는 기준선 10 아래라 누적되지 않음 |
| M (위험) | 판정선의 **5배** | 측정한 약한 공격은 판정선의 2배, 강한 공격(초당 1,000개)은 20배 → 그 사이 |
| 빠른 포트 스캔 | 4초에 실패 응답 **15개** 이상 + 연결 시도의 50% 이상 실패 | Zeek 15개, Jung 2004 실패 비율. 정상 최대 4초 2개 |
| 느린 포트 스캔 | 5분에 실패 응답 **30개** 이상 + 최근 4초에 실패 1개 이상 | Zeek 5분 창. 정상 최대 5분 13개 × 2 → 30. 5분 동안 정상 연결도 수백 개 섞이므로 비율은 보지 않음 |
| UDP 스캔 | 4초에 ICMP 도달 불가 **4개** 이상 | 리눅스는 도달 불가를 처음 6개 뒤 초당 1개로 제한 → 300포트 스캔에도 6개. 정상 최대 4초 2개 × 2 |
| 스캔 실패 응답의 상한 | 한 주기의 실패 응답은 **보낸 연결 시도의 2배까지만** 센다 | 스캔이라면 실패는 자기가 보낸 시도에 대한 답이다. 서버가 이 PC의 오래된 연결을 한꺼번에 끊으며 보낸 RST 묶음(Slow HTTP 뒤처리)은 스캔이 아니다 |
| 서비스 악화 | 확인 ping 손실 **25%** 이상 또는 평균 왕복 **10ms** 이상이 **2회 연속** | 정상 10분(303회) 최대: 손실 11.1%(ping 1개, 연속 없음), 평균 왕복 4.4ms → 2배 |
| Slow HTTP | 한 PC의 느린 요청 **10개** 이상 (2회 연속) | 정상 측정 0개. Slowloris 기본값 150개는 15배 → 위험 |
| 내부 확산 | 5분에 없는 내부 주소 **25개** 이상 + 최근 4초에도 새 주소 | Zeek(5분 안에 서로 다른 호스트 25개 연결 실패). 정상 측정 0개 |
| 경고 속도 제한 | 그 종류 패킷만 **초당 50개** | 공격 최소 규모와 같음. 정상 사용자의 같은 종류 패킷(UDP 2.5, ICMP 18.5)은 그대로 지나감 |

### 2.4 공격별 판정선과 측정 크기 (H_attacker, 사전 학습값 기준)

| 공격 | 판정 규칙 | 판정선 | 측정 크기 (초당, 평균) | 판정 |
|---|---|---|---|---|
| SYN Flood | gap > 10 동안 초과분 누적 ≥ 100 | 50 | 약 84 / 강 834 | 경고 (2배) / 위험 (20배) |
| UDP Flood | udp ≥ max(10 × 0.49, 50) | 50 | 약 84 / 강 833 | 경고 / 위험 |
| ICMP Flood | icmp ≥ max(10 × 0.98, 50) | 50 | 약 84 / 강 792 | 경고 / 위험 |
| 포트 스캔 (TCP, 1,000포트) | 4초 실패 ≥ 15 | 15 | 실패 응답 250 | 위험 |
| 포트 스캔 (TCP, 초당 2포트) | 5분 실패 ≥ 30 | 30 | 실패 응답 2 | 경고 |
| 포트 스캔 (UDP, 300포트) | 4초 도달 불가 ≥ 4 | 4 | 도달 불가 5 ~ 6 (4초) | 경고 |

H_legit의 ICMP 판정선은 10 × 17.9 = 179 (평소 ping이 많은 사용자는 판정선도 그만큼 높다).
측정 크기가 보낸 속도(100 · 1,000)보다 조금 작은 것은 공격 시작 · 끝 보고에 공격이 일부만 들어 있어서다.

### 2.5 방어를 켠 검증 (2026-10-28)

새 컨트롤러 + 추론 워커(기준표 모드, 위 평소값 파일)를 켜고, 정상 5분 뒤 공격 9종을 30초 간격으로 넣었다.
H_legit은 그동안 0.05초마다 ping을 보내 정상 사용자 손실을 쟀다.
실행: 컨트롤러 · Redis · `python -m model.inference_worker --log events.jsonl` 실행 후
`sudo python3 -m harness.verification.criteria_measure --run --defense --out <폴더> --normal-seconds 300 --surge-at 120,220`,
분석은 `criteria_measure --e2e <폴더> --events events.jsonl`.

| 구간 | 판정 → 대응 | 탐지까지 (공격 시작부터) | 정상 사용자 ping 손실 |
|---|---|---|---|
| 정상 5분 (접속 몰림 2회 포함) | 경고 · 위험 0회, 주의도 0회 | — | 5,206회 중 2 (0.04%) |
| 쉬는 구간 9개 | 경고 · 위험 0회 | — | 0 ~ 0.2% |
| SYN Flood 강 (초당 1,000) | 위험 → 격리 + 우회 | 4.35초 | 0% |
| UDP Flood 강 (초당 1,000) | 위험 → 격리 + 우회 | 4.23초 | 8.8% |
| ICMP Flood 강 (초당 1,000) | 위험 → 격리 + 우회 | 4.10초 | 10.2% |
| SYN Flood 약 (초당 100) | 경고 → SYN만 초당 50개 | 3.81초 | 0% |
| UDP Flood 약 (초당 100) | 경고 → UDP만 초당 50개 | 3.70초 | 0.6% |
| ICMP Flood 약 (초당 100) | 경고 → ICMP만 초당 50개 | 3.57초 | 1.7% |
| UDP 스캔 (300포트, 1초) | 경고 → SYN · UDP 초당 50개 | 4.25초 (다시 실행) | 0% |
| 느린 TCP 스캔 (초당 2포트, 20초) | 경고 → SYN · UDP 초당 50개 | 12.37초 | 0% |
| 빠른 TCP 스캔 (1,000포트) | 위험 → 격리 + 우회 | 4.26초 | 0% |

- **경고 단계 속도 제한 실측:** 약한 UDP Flood 중 미터에 들어온 1,610개 중 801개, 약한 ICMP Flood 중 1,617개 중 812개를 버렸다 (초당 100개 → 50개).
  10초 동안 경보가 없으면 해제됐다.
- **조치 시간:** 경보 뒤 50ms 안에 격리 · 우회 또는 속도 제한. 마지막 경보 뒤 약 10초에 복구 · 해제.
- **탐지 지연이 약 4초인 이유:** 2초마다 세고 2회 연속 확인한다. 이번 실험은 공격이 매번 보고 직후에 시작돼
  첫 보고에 공격이 거의 없었다 (가장 늦은 경우). 8주차 목표 3.2초보다 약 1초 늦다 → §2.7에서 1초 주기로 바꿔 2초대로 줄였다.
- **강한 UDP · ICMP Flood의 정상 사용자 손실:** 손실은 공격 시작 0.5초 ~ 6.5초(격리 2초 뒤)에 몰려 있다. 같은 시간에 서버가
  내보낸 ICMP가 초당 19개 → 9 ~ 13개로 줄었다. 서버가 가짜 출발지로 보내려는 응답(ICMP 도달 불가 · echo 응답)이
  나가지 못하고 쌓이면서 정상 ping 응답까지 밀린 것으로 보고 있다 (테스트베드에 기본 게이트웨이가 없음). SYN Flood는
  ICMP를 쓰지 않아 손실이 없었다. 확인 중.
- 이 실험의 UDP 스캔은 도달 불가 기준을 3개로 둔 상태였다. 기준을 4개로 올린 뒤 UDP 스캔만 다시 실행해 탐지를 확인했다 (도달 불가 5개, 4.25초에 경고 → 속도 제한, 정상 구간 경보 0회).

### 2.6 추가 기준 검증 (서비스 악화 · Slow HTTP · 내부 확산, 2026-10-28)

방어를 켠 같은 방식으로, 새 기준만 따로 실험했다 (정상 2~5분 뒤 시나리오, 사이 30초 쉼).

| 시나리오 | 판정 → 대응 | 탐지까지 | 서비스 상태 확인 (가장 나쁜 보고) |
|---|---|---|---|
| 정상 5분 (서버 연결 · 없는 주소 · 확인 ping 포함) | 경고 · 위험 0회, 주의 0회 | — | 손실 0%, 왕복 3.1ms |
| 약한 UDP Flood (초당 100, 비교용) | 경고 → UDP만 초당 50개 | 4.4초 | 손실 10% (1회) |
| 중간 ICMP Flood (초당 200 = 판정선 4배) | 경고 → ICMP만 초당 50개 | 4.3초 | 손실 70% 1회 → 속도 제한 뒤 10% → 0%: 2회 연속이 아니라 위험으로 안 올림 |
| 약한 UDP Flood + 서버 장애(서버가 내보내는 패킷 40% 버림) | 경고 → 2초 뒤 **서비스 악화로 위험** → 격리 + 우회, 장애가 풀린 뒤 복구 | 경고 3.1~4.3초, 위험 5.1~10.3초 (두 번 실험) | 손실 40~60% 연속 |
| Slow HTTP 30개 | 경고 → 새 연결(SYN) 초당 50개 | 24초 (20초가 지나야 느린 요청) | 손실 0% |
| Slow HTTP 150개 (Slowloris 기본값) | 위험 → 격리 + 우회, 서버가 30초 뒤 남은 연결을 끊은 다음 복구 | 24초 | 손실 0% |
| 내부 확산 (없는 내부 주소 56개, 445 포트, 초당 10개) | 경고 → 새 연결(SYN) 초당 50개 | 4.9초 | 손실 0% |
| 특수 상황 재학습: 초당 150개 UDP를 계속 보내고(판정선 3배, 승인 전 경고) 30초 뒤 90초 재학습 승인 | 승인 7초 뒤 정상(새 평소값), 기간이 끝나자 1초 만에 사전 학습값으로 돌아가 다시 주의 → 경고 | — | — |

- 중간 ICMP Flood는 경고 단계의 속도 제한만으로 서비스가 회복돼 격리까지 가지 않았다. 단계 대응이 의도대로 동작한 경우다.
- 서버 장애는 이 실험 환경의 커널에 `tc netem`이 없어 `iptables -m statistic`으로 만들었다.
- 처음 실험에서는 Slow HTTP가 끝나고 30초 뒤 서버가 남은 연결 150개를 한꺼번에 끊으며 RST를 보내, 마침 시작한 내부 확산 실험이
  포트 스캔으로 잘못 잡혔다. 스캔 실패 응답을 보낸 연결 시도의 2배까지만 세도록 고친 뒤 다시 실험해 내부 확산으로 정확히 잡았다.
- 서버 장애 실험 중 테스트용 DNS 응답기가 보내기 실패로 멈춰, 그 뒤 두 PC의 DNS 질의가 모두 '도달 불가'로 돌아왔다.
  이것이 5분 창에 쌓여 Slow HTTP 뒤 쉬는 구간에서 포트 스캔 경고가 났다. 응답기가 보내기 실패에도 죽지 않게 고친 뒤
  서버 장애 · Slow HTTP를 다시 실험해, 장애 뒤 실패 응답이 정상 수준(초당 0.01~0.03개)으로 돌아오고 Slow HTTP 뒤 쉬는 구간 경보가
  0회인 것을 확인했다 (서버 장애 실험도 같은 결과: 경고 → 서비스 악화로 위험).

### 2.7 탐지 시간 단축: 종류별 개수를 1초마다 (2026-10-28)

2초 주기에서는 "2회 연속 확인" 때문에 공격이 보고 직후에 시작하면 확정까지 약 4초가 걸렸다 (§2.5, 목표 3.2초).
종류별 개수만 1초마다 읽도록 바꿨다 (포트 통계 · 서비스 상태 · 관제탑은 그대로 2초). 판단 프로그램의 창은 보고 횟수가 아니라
초로 바꿔서(스캔 4초 · 5분, 주의 해제 4초, 학습 재개 10초, 평소값 10분 기억) 뜻은 그대로다.

**1초 단위 정상 10분 (같은 규칙: 정상 최대 × 2)**

| 지표 (초당) | 정상 최대 (2초 보고) | 정상 최대 (1초 보고) | 최소값 · 기준 |
|---|---|---|---|
| SYN | 55 | 55 | 110 (그대로) |
| SYN − (FIN+RST) | 3.5 | **8** | 10 → **20** |
| UDP | 2.5 | 4 | 10 (그대로) |
| ICMP | 18.5 | 19.2 | 40 (그대로) |
| 실패 응답 | 4초 2개, 5분 13개 | 같음 | 그대로 |
| 서비스 확인 평균 왕복 | 4.4ms | **5.7ms** | 10 → **12ms** |
| 느린 요청 · 없는 주소 | 0 | 0 | 그대로 |

- SYN Flood 누적 H는 100 → **50**: 1초 보고에서 약한 공격(초당 100개)의 기준선 초과분이 한 번에 약 80개라, 전처럼 "한 보고 안에 넘음"이 되게 했다.
  정상은 기준선(20)을 넘지 않아 누적이 쌓이지 않는다.
- N은 10 그대로: 1초 보고에서 UDP 최대/평균이 8배로 튀지만 평균이 초당 0.5개라 판정선은 공격 최소 규모(50)가 정한다.
  N이 실제로 쓰이는 ICMP(평균 18)는 최대/평균 1.06배.
- 평소값 파일을 1초 보고 590초로 다시 학습했다. 같은 정상 10분을 다시 돌려 보니 594회 모두 정상.

**방어를 켠 전체 실험 (정상 5분 + 공격 14종, 공격 시작을 0~2초 무작위로 늦춤)**

| 공격 | 판정 → 대응 | 탐지까지 (2초 주기 → 1초 주기) |
|---|---|---|
| SYN · UDP · ICMP Flood 강 | 위험 → 격리 + 우회 | 4.1~4.4초 → **1.8~2.5초** |
| SYN · UDP · ICMP Flood 약 | 경고 → 그 종류만 초당 50개 (약한 ICMP는 서비스 악화 2회 연속으로 3초 뒤 위험) | 3.6~3.8초 → **2.4~2.6초** |
| 중간 ICMP (초당 200) | 경고 → 서비스 악화로 위험 | 4.3초 → **2.4초** |
| 약한 UDP + 서버 장애 | 경고 → 서비스 악화로 위험 | 3.1~4.3초 → **2.3초** |
| UDP 스캔 / 빠른 TCP 스캔 | 경고 / 위험 | 3.5 / 4.3초 → **2.4 / 1.7초** |
| 느린 TCP 스캔 (5분 창) | 경고 | 12.4초 → 10.5초 |
| 내부 확산 | 경고 | 4.9초 → 4.1초 |
| Slow HTTP 30 / 150개 | 경고 / 위험 | 24초 → 22.6초 / 처음 3.5초에 SYN Flood 경고, 이어서 Slow HTTP 위험 |

- **정상 5분: 경고 · 위험 0회, 주의 0회.** 쉬는 구간 15개(공격 사이 · 마지막 공격 뒤) 중 경보가 난 곳은 느린 TCP 스캔 바로 뒤 1곳뿐이다:
  5분 안에 스캔한 PC(공격자)가 다시 실패 응답을 받아 "아직 스캔 중"으로 본 것이다 (느린 스캔 규칙의 정의대로).
- **Slow HTTP 150개:** 처음 3초 동안 연결을 초당 약 48개씩 열고 닫지 않아 SYN − (FIN+RST)가 기준선을 넘었고, SYN Flood 경고(새 연결 제한)가
  먼저 났다. 20초 뒤 느린 요청 150개로 Slow HTTP 위험이 됐다.
- **정상 사용자 손실 (ping):** 전체 1.57%. 강한 UDP · ICMP Flood 7.0% · 8.9% (2초 주기 때 8.8% · 10.2%, 격리가 빨라진 만큼 줄었다).
  약한 · 중간 ICMP Flood는 서버의 ICMP 응답이 밀려(손실 5.7 · 7.0%) 서비스 악화로 위험까지 올라갔다.
- 공격 14종 중 탐지 창 자체가 긴 것(느린 스캔 5분 · 내부 확산 · Slow HTTP 20초)을 빼면 모두 목표 3.2초 안이다 (가장 늦은 것 2.6초).

## 3. 위험도 단계와 대응

| 단계 | 조건 | 대응 (컨트롤러) |
|---|---|---|
| 정상 | 모든 지표가 기준선 이하 | 없음 |
| 주의 (WATCH) | 지표 하나라도 기준선 초과 | 기록만 (경보 없음) |
| 경고 (WARNING) | 공격 종류 확정 (2회 연속), 세기 < 5 | 그 포트의 **그 공격 종류 패킷만** 초당 50개로 제한 (UDP Flood면 UDP만, ICMP Flood면 ICMP만, SYN Flood · Slow HTTP · 내부 확산이면 새 연결(SYN)만, 포트 스캔이면 SYN과 UDP). 마지막 경보 뒤 10초 동안 경보가 없으면 해제 |
| 위험 (DANGER) | 공격 종류 확정 + (세기 ≥ 5 **또는 서비스 악화 2회 연속**) | 격리 + 우회 (기존 방식, FSM 쿨다운 5초 / 10초) |

세기 = 지표 값 / 판정선 (포트 스캔은 실패 응답 수 / 기준 개수). 경고 중 위험 경보가 오면 속도 제한을 지우고 격리한다. 격리 중 경고 경보가 오면 격리를 유지한다.
서비스 악화만으로는 아무 포트도 막지 않는다 (누가 원인인지 모르므로). 공격 종류가 확정된 포트를 위험으로 올릴 때만 쓴다.

## 4. 평소값

- **사전 학습:** 정상 트래픽만 흐르는 동안 평소값을 학습해 `model/criteria_baseline.json`에 저장한다.
  (`python -m model.inference_worker --learn 600` 또는 `criteria_measure --analyze <폴더> --baseline-out <파일>`)
- **시작:** 저장된 값으로 바로 방어한다. 파일이 없으면 최소값만으로 판단한다 (고정 기준).
- **갱신:** 보고마다 EWMA(최근 약 10분 기억, 보고 주기 dt초면 α = 2 / (600 / dt + 1)). 그 포트가 10초 연속 정상일 때만 갱신한다.
- **상하한:** 갱신된 평균 · 표준편차는 사전 학습값 ~ 2배 사이에서만 움직인다.
- **특수 상황 재학습 (관리자 승인):** 관제탑 "특수 상황 재학습" 버튼 → `POST /api/control/relearn` (`minutes` 1~240, `reason`,
  포트를 안 주면 모든 접속 포트, 관리자 토큰 규칙은 수동 제어와 같음) → `RELEARN` 명령 → 추론 워커가 승인된 기간 동안 **양(SYN · UDP · ICMP 초당 수)만**
  상하한 없이 빠르게(최근 약 1분) 다시 배운다. 경고 중이어도 배우지만, 위험 크기(판정선의 5배 이상)는 배우지 않는다.
  짝이 안 맞는 연결 · 실패 응답 같은 공격 신호는 다시 배우지 않는다. 기간이 끝나면 사전 학습값으로 돌아간다.

## 5. 한계와 아직 없는 것

- **재학습 승인은 사람이 판단한다:** 관제탑의 "특수 상황 재학습" 창에서 기간 · 사유를 넣어 승인한다. 늘어난 트래픽이 정상인지는
  관리자가 SYN · FIN 짝, 실패 응답, 서비스 상태를 보고 정한다. 승인 중에 들어온 경고 크기의 Flood는 평소로 배울 수 있다.
- **서비스 상태 확인은 ICMP:** 정상 사용자의 웹(TCP) 경험과 다를 수 있다. 확인 ping은 컨트롤러가 받으므로 컨트롤러가 바쁘면 왕복 시간이 늘어난다.
- **Slow HTTP 수집기는 서버에서 돌아야 한다:** 테스트베드에서는 `nsenter`로 h_server의 네트워크 공간에서 `ss`를 읽는다.
  브라우저처럼 연결을 오래 열어 두는 클라이언트는 응답을 이미 받았으므로 느린 요청으로 세지 않는다.
- **내부 확산은 '없는 주소'만 센다:** 있는 PC의 닫힌 포트(445 · 3389)에 대한 실패는 포트 스캔 규칙(실패 응답)으로 잡힌다.
  ARP 캐시에 남은 주소는 다시 묻지 않으므로 같은 주소를 반복해 찾는 경우는 세지 않는다.
- **서로 다른 포트 수:** 카운터는 개수만 세므로, 포트 스캔은 실패 응답 개수와 실패 비율로 판단한다.
  그래서 죽은 서비스(예: 멈춘 DNS 서버)를 1분 넘게 계속 다시 두드리는 PC는 느린 스캔(5분 30개)처럼 보일 수 있다.
  이때는 경고(새 연결 초당 50개 제한)라서 그 PC의 정상 사용은 거의 막히지 않는다.
