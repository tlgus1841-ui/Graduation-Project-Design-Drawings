## 1. 목적

정상 통신 → 스푸핑 공격·탐지 → 자율 격리·우회 → 자가 복구의 4단계가 실제 Mininet 위에서 끊김 없이 하나의 루프로 도는지 확인하고, 그동안 정상 사용자의 통신이 얼마나 영향을 받는지 측정한다. 목표는 **공격 중 정상 트래픽 손실률 ≤ 2%**이다.

## 4. 측정 중 발견한 문제 2건

### 4.1 측정 도구 문제: ping이 공격 중 멈춤 (수정 완료)

첫 측정에서 공격 20초 동안 ping 응답이 하나도 없었는데, 순번(icmp_seq)은 끊기지 않고 이어졌다. 손실이 아니라 **ping이 아예 보내지 않은 것**이다. ping 출력을 가상 호스트의 터미널에 쌓아두고 읽지 않아 버퍼가 가득 차면서 ping이 멈췄다. 출력을 파일로 돌린 뒤에는 80초 내내 끊김 없이 측정되었다. 수정 전 결과는 사용하지 않았다.

### 4.2 설계 문제: 차단 규칙과 우회 규칙의 우선순위 충돌 (명세 수정 제안)

명세(§3.3)는 차단(`in_port=2 → drop`)과 우회(`ip, nw_dst=10.0.0.4 → S3 방향`)를 **모두 Priority 100**으로 정했다. 공격 패킷은 두 규칙에 동시에 해당한다. OpenFlow는 우선순위가 같은 규칙이 겹칠 때 어느 쪽을 적용할지 정하지 않는다.

| 조건 | 차단 규칙에 걸린 공격 패킷 | S1 우회 규칙을 탄 패킷 | 판정 |
|:---|:---:|:---:|:---:|
| 명세대로 (둘 다 100) | **0** | 27,607 | 공격이 우회로로 서버까지 전달됨 |
| 차단 200 > 우회 100 | **26,095** | 267 (= 정상 ping) | 공격만 차단 |

명세대로면 격리 명령이 나가도 공격 패킷은 **우회 경로를 타고 서버에 도착**했다. 차단 규칙의 우선순위를 우회보다 높이자 공격 패킷은 S1에서 버려지고, 우회 경로에는 정상 ping만 지나갔다.

→ **명세 수정 제안:** ISOLATE drop 규칙 Priority를 우회(100)보다 높게(예: 200) 둔다. 또는 우회 규칙의 일치 조건에 정상 사용자 포트(`in_port=1`)를 넣는다. (Tech Lead 확인 필요, 명세 §8 Q5)

## 5. 측정 결과 (차단 200 > 우회 100, 3회)

| 지표 | 1회 | 2회 | 3회 | 평균 | 목표 |
|:---|:---:|:---:|:---:|:---:|:---:|
| 공격 패킷 (S1:2 수신) | 34,201 | 35,632 | 35,643 | 35,159 | - |
| 공격 시작 → 첫 경보 | 2.99초 | 1.01초 | 1.03초 | 1.68초 | - |
| 탐지 확정 → 차단·우회 설치 완료 | 78.4ms | 78.6ms | 78.1ms | **78.4ms** | ≤ 100ms |
| 격리 중 S1에서 버려진 공격 패킷 | 26,095 | 30,517 | 27,742 | 28,118 | - |
| 격리 중 서버로 샌 공격 패킷 | 0 | 0 | 0 | **0** | 0 |
| 차단 / 해제 횟수 | 1 / 1 | 1 / 1 | 1 / 1 | **플래핑 0** | 0 |
| 공격 종료 → 자동 복구 | 12.64초 | 13.49초 | 12.06초 | 12.73초 | 쿨다운 10초 |
| **정상 ping 손실 (전체)** | 0 / 1,432 | 0 / 1,442 | 0 / 1,438 | **0%** | ≤ 2% |
| 정상 ping 손실 (공격 구간) | 0 / 364 | 0 / 384 | 0 / 375 | **0%** | ≤ 2% |

- **첫 경보 → 차단:** 약 2.07초. 오탐을 막기 위해 2초 주기 통계 2번 연속 확인(명세 T1) 후 차단하기 때문이다.
- **규칙 설치 시간:** 우회 4개 약 61ms, 차단 1개 약 16ms (`ovs-ofctl` 기준).
- **관제탑 반영:** 경보·격리·복구가 브라우저 배지에 반영되기까지 40~200ms (200ms 간격 관찰 기준). 화면에서 S1:3(S2 방향) 트래픽이 0으로, S1:4(S3 방향)가 정상 사용자 트래픽으로 바뀌는 것이 실데이터로 확인되었다.
- 첫 회 "첫 경보" 2.99초는 공격 시작이 통계 수집 직후에 걸려 한 주기(2초)를 더 기다린 경우다.

**판정: 통과.** 4단계 루프가 3회 모두 사람 개입 없이 완결되었고, 공격 중 정상 트래픽 손실 0%(목표 ≤ 2%), 격리 후 서버 도달 공격 패킷 0, 플래핑 0.

## 6. 한계와 후속

| 항목 | 내용 |
|:---|:---|
| AI 탐지 | 규칙으로 대체했다. Isolation Forest 연동 후 같은 시나리오로 재측정한다 (13주차 F1 목표 ≥ 0.95). |
| 방어 실행 | `ovs-ofctl`로 대체했다. 컨트롤러가 FlowMod로 설치하면 반응 시간은 다시 측정한다. |
| 관제탑 단계 | 실데이터 모드에는 FSM 단계 채널이 없어 `RESTORING` 단계와 복구 완료 알림이 나오지 않는다 (명세 Q3). 토폴로지 지도 색도 정적이다 (컨트롤러가 `sdn:topology:sync`를 발행하면 반영). |
| 피처 계산 | Mininet 종료 시 포트 카운터가 리셋되며 ΔPPS가 약 9.2×10¹⁸으로 계산되는 경우가 있었다. 방어 루프에서는 버리도록 했고, 피처 계산기에도 같은 보호가 필요하다 (Domain Dev 확인). |
| 환경 | OVS 유저스페이스 데이터패스. 손실률·규칙 동작은 같지만 처리 속도는 커널 데이터패스와 다를 수 있다. |

redis-server --daemonize yes

SDN_MOCK=0 uv run uvicorn api.main:app --port 8000 &
# 2) 임시 방어 루프 (root, 차단 우선순위 200)

uv run python -m harness.verification.e2e_scenario --analyze run.json --events events.jsonl
