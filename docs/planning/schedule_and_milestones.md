## 1. 계획 수정 배경 및 목적

### 1.1 기존 일정 계획(v1.0)의 문제점
1. **순차적(Waterfall) 의존성 병목:** 인프라(Mininet/Ryu)가 완성되어야 AI가 데이터를 수집하고, AI가 완성되어야 웹 관제탑이 연동되는 직렬 구조로 인해 개발자 간 대기 시간 발생.
2. **SDN 제어 평면 블로킹 위험 미반영:** Ryu 내부에서 직접 ML 추론을 수행하려던 구조적 결함으로 인해, 비동기 IPC(Redis Pub/Sub) 및 독립 AI 워커 분리 일정이 누락됨.
3. **OpenFlow 다중 홉 우회 라우팅 공수 과소평가:** 단일 스위치 포트 변경(`OFPFC_MODIFY`) 수준으로 계획되어, 실제 다중 홉 토폴로지에서의 경로 계산(Dijkstra) 및 선제적 플로우 주입(`OFPFC_ADD`) 공수가 반영되지 않음.
4. **자가 복구 플래핑(Flapping) 위험:** 단순 타임아웃 차등에만 의존하여 공격 지속 시 라우팅 플래핑이 발생하는 결함이 있었으며, 명시적 FSM(상태 머신) 구축 일정이 부재함.

### 1.2 수정 계획(v2.0)의 핵심 개선 방향
* **Contract-First 인터페이스 동결:** 1~3주차에 통신 프로토콜(Redis Channel, WebSocket JSON Schema, REST API)을 선제 확정하고, Mock Generator를 구축하여 웹·AI·인프라 3인이 4주차부터 완전 병렬 개발 수행.
* **마이크로서비스 아키텍처 반영:** Ryu(Docker Python 3.8), AI Worker(Python 3.10), FastAPI(Python 3.10), React 18(Node 20) 간의 독립 실행 및 비동기 메시지 버스 연동 마일스톤을 주차별로 명확히 분할.
* **실전적 5대 파생 피처 엔지니어링 구축:** 무거운 공개 데이터셋 대신 SDN 환경에서 즉시 계산 가능한 실시간 피처 파이프라인($\Delta \text{PPS}$, $\Delta \text{BPS}$, $\text{BPP}$ 등) 개발 일정 배정.
* **검증 가능한 주차별 마일스톤 정의:** 매주 구체적인 정량적 완료 기준(Definition of Done)과 산출물을 명시하여 학기 중 A4 정기 보고서 작성 및 학기말 시연 평가를 철저히 대비.

## 6. 기존 계획 대비 핵심 수정 내역 (Comparison Matrix)

| 검토 영역 | 기존 계획 (v1.0) | 수정 계획 (v2.0) | 수정 사유 및 기대 효과 |
|:---|:---|:---|:---|
| **개발 프로세스** | 순차적(Waterfall) 방식<br>(인프라 ➔ AI ➔ 웹 순차 진행) | **AI 하네스 엔지니어링 기반 3인 병렬 개발**<br>(Pydantic IPC 스키마 동결 후 Mock 하네스 기반 동시 개발) | 특정 파트 지연이 전체 프로젝트 병목으로 전이되는 위험을 원천 차단하고 개발 속도 2배 향상 |
| **제어 평면 아키텍처** | Ryu 백그라운드 스레드에서 ML 직접 추론 | **Ryu(Docker)와 AI Worker(독립 프로세스)를 Redis IPC로 분리** | Ryu Greenlet 코루틴 블로킹으로 인한 스위치 연결 끊김(OVS Disconnect) 참사 방지 |

## 7. 주차별 리스크 관리 및 대체 대책 (Contingency Plan)

| 발생 가능한 리스크 | 영향도 | 발생 주차 | 예방 및 비상 대응 대책 (Fallback) |
|:---|:---:|:---:|:---|
| **Ryu와 OVS 간 OpenFlow 1.3 핸드셰이크 실패** | 높음 | 4~5주차 | • Docker 구동 시 반드시 `--net=host` 옵션 적용<br>• OVS bridge의 프로토콜 버전을 `OpenFlow13`으로 명시적 고정 (`ovs-vsctl set bridge s1 protocols=OpenFlow13`) |
| **Scapy 패킷 폭주 시 Linux Checksum 누락** | 중간 | 5~6주차 | • 패킷 생성 시 IP/TCP 체크섬 필드 명시적 삭제 (`del pkt[IP].chksum`)를 통해 커널 자동 재계산 유도 |
| **WebSocket 새로고침 시 ASGI 서버 비정상 종료** | 높음 | 5~6주차 | • FastAPI `ConnectionManager` 내 `disconnect()` 핸들러에서 세션 즉각 제거 및 Stale 세션 자동 정리 try-except 블록 적용 |

| **라이브 시연 시 현장 네트워크/시스템 예기치 않은 오류** | 치명적 | 15~16주차 | • 15주차에 실제 구동 화면을 무편집 고화질 영상으로 사전 녹화하여 백업 확보<br>• 원클릭 자동 복구 및 초기화 스크립트(`reset_env.sh`) 구비 |
